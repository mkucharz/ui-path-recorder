Playwright · one committed plan · figures a reviewer can trust

Record a path through a live UI once.
Re-run it when the docs go stale.

A walkthrough is one path through an application: open this, type that, click here, take a picture where a reader needs to see. This keeps that path as a committed JSON plan and executes it in a pinned browser — so the figures in your documentation stop depending on who held the screenshot tool. 

npx skills add mkucharz/ui-path-recorder --skill path-recorder -g

The skill is the way in: install it once, then ask your agent for the figures. The recorder itself runs on Node 20+, and ffmpeg is only needed for --video. Running the CLI directly works too.

01

Why this exists

Every hand-taken documentation screenshot eventually goes wrong in the same few ways, and all of them are invisible until a reader notices:

  • The operator's language leaks in. An app with no stored preference resolves its UI language from Accept-Language. One real page shipped Polish screenshots on an English tutorial.
  • The operator's theme leaks in. An app that applies a stored theme after first paint gives a shot taken a fraction too early the wrong one.
  • The operator's extensions leak in. A password manager's autofill menu, injected into the page's DOM, lands inside the picture.
  • The operator's account leaks in. Their email, their avatar, their organisation.
  • Nobody knows how the picture was taken — so "just re-shoot it" means clicking through the flow again from memory, and the prose drifts away from what the UI now does.

A plan fixes the first four by construction. Committing it is the answer to the fifth.

02

How it works

Four steps, one artefact each — and the artefact is the only thing the next step reads.

  1. plan.json

    Commit the path, not the pictures. A plan names the URL, the locale, the theme, the device pixel ratio, every step, and the points where a figure is due. expect states what must be on the screen.

  2. path-shots

    Run it in a pinned browser. The runner refuses to write a figure when the screen does not prove it is the right one, and records the run at human pace when a video is asked for.

  3. review.html

    Review before publishing. Each figure at its real pixels, the size the app drew on screen, the text the plan asserted — and a slideshow that walks the figures in run order.

  4. figures/

    Publish the same run. Figures ingest to WebP with the pixel bounds a document should size them to; the video ships with chapters, and the captions were already in the plan.

The guards

Each of these is a failed run, not a wrong picture. A figure is written only for a screen the plan can prove:

expect per figure
the screen lost an element id the path depends on, or the words the document claims
language
the page resolved another locale (lang="pl" under an en-US plan)
theme
the page painted light under a dark plan — the theme had not settled
waitHidden
a control the server rendered visible and the script later hides
clip validation
the subject selector matched nothing
plan validation
a mistyped step key or a duplicate figure id, refused before a browser opens

On failure the run leaves failures/<stamp>--<step>.txt, and its last section is on screen: — every button, link and input the page was actually showing, so the plan is fixed from evidence instead of someone's description of it.

03

Use it

A run is a plan plus the command that plays it. The plan is the artefact you write, commit and review — the URL, the credentials by environment variable, the steps, and which of them are figures — so start there and the command has nothing left to decide.

A plan

One JSON file per walkthrough. Steps run in order, names are for humans, and a step that carries a shot becomes a figure: 

{
  "tutorial": "signin",
  "baseUrl": "${INSTANCE_URL}",
  "locale": "en-US",
  "viewport": { "width": 1600, "height": 900 },
  "colorScheme": "dark",
  "vars": {
    "email": { "literal": "admin@example.com" },
    "password": { "env": "INSTANCE_PASSWORD" }
  },
  "steps": [
    { "name": "open", "goto": "/login" },
    { "name": "dismiss the cookie banner", "clickIfPresent": { "selector": "#cookie-deny" } },
    { "name": "sign-in card", "expect": { "selector": ["#email", "#password"] },
      "shot": { "id": "01-signin", "clip": "main.card" } },
    { "fill": { "selector": "#email", "value": "${email}" } },
    { "type": { "selector": "#password", "value": "${password}" } },
    { "click": "#submit" },
    { "waitFor": { "selector": "#dashboard" } },
    { "expect": { "selector": ["#dashboard"] }, "shot": { "id": "02-app" } }
  ]
}

Full reference: plan-format.md · machine-readable: schema.json · the example plans this page's figures come from: plans/examples.

Play it: thirty seconds, no account

The repo ships a fixture plan and a fixture app that is hostile in the three ways real apps are: a cookie banner, a control painted before its script hides it, and a second screen that replaces the first without changing the URL. Play that plan before writing your own: 

node test/serve.mjs --port 8099 &

FIXTURE_URL=http://127.0.0.1:8099 FIXTURE_PASSWORD=correct-horse \
  node scripts/path-shots.mjs test/plans/fixture.plan.json --review

open captures/fixture-*/review.html

Those two variables belong to the fixture plan, not to the tool: the plan declares "baseUrl": "${FIXTURE_URL}" and "password": {"env": "FIXTURE_PASSWORD"}, so the run follows whatever port the server bound and no credential sits in the plan.

Install it as a skill

The skill is the intended way in. SKILL.md teaches a coding agent the workflow — find the flow in the source, write the plan, run it, read the failure, publish the figures — and the rules that make a figure worth trusting. You ask for documentation figures; the agent writes the plan. 

npx skills add mkucharz/ui-path-recorder --skill path-recorder -g

skills is the agent-skills CLI: it installs into whichever of OpenCode, Claude Code, Codex, Cursor and the rest it finds, and records what it installed in skills-lock.json. Pin a release rather than a branch: 

npx skills add mkucharz/ui-path-recorder@v0.5.0 --skill path-recorder -g

No CLI, or an agent that just reads a folder? The skill is one directory — clone it into the skills folder your agent watches, or unpack the release tarball there: 

git clone https://github.com/mkucharz/ui-path-recorder \
  ~/.config/opencode/skills/path-recorder   # OpenCode, Codex, Cursor
git clone https://github.com/mkucharz/ui-path-recorder \
  ~/.claude/skills/path-recorder            # Claude Code

The flags that matter

FlagWhat it does
--reviewwrite review.html into the run directory
--videorecord the walkthrough and drive it like a person (needs ffmpeg)
--narrationspeak every step, muxed in (needs a system ffmpeg with libopus)
--narration-enginesay (macOS, the default) or elevenlabs (needs ELEVENLABS_API_KEY, or a gitignored .env)
--voice, --narration-modelpin who reads it, so a re-record sounds like the last one — see Voice
--out <dir>the run directory (default captures/<tutorial>-<timestamp>)
--only <id>replay up to that figure and stop
--profile <dir>keep a signed-in session on this host, for flows behind a login
--speed <n>scale every human delay: 1 natural, 20 a fast test run

04

It can speak

A walkthrough watched on a phone, in a taxi, on a train: the screen explains the steps, and nothing says why. --narration speaks each step and muxes the voice into the recording. 

{
  "video": { "narration": { "engine": "elevenlabs", "fit": "line" } },
  "steps": [
    { "caption": "Sign in.",
      "say": "Sign in with the account you already use — this walkthrough installs into your own workspace.",
      "goto": "/signin" }
  ]
}

video.narration is the plan asking for narration, and its presence is enough. say defaults to caption, so a plan that writes neither speaks its own subtitles and the pill, the .vtt and the voice cannot disagree. --no-narration records a silent copy without editing the plan, and its .vtt falls back to the captions rather than transcribing a voice nobody hears.

A caption read aloud is not a sentence

That default is convenient, not free. "Choose Sign in." is a good pill and an abrupt thing to hear, and six of them in a row sound like a form reading itself out. Write the line you would say while pointing at the same screen — the verb the viewer is doing, something they already know (“the account you already use”), and what happens next (“… and you're in”). The run names the two shapes worth a second look, and speaks what it was given: 

warning: step #4 (fill the password) is spoken as "Then the password."
         — a label, not a sentence
warning: step #5 (sign in) is written as an instruction to a control:
         "Choose Sign in."

The picture waits for the sentence

A spoken line runs two to five seconds and a step is often shorter, so narration is a two-pass run: every line is synthesized before the browser opens, and the step that starts a cue waits max(hold, line + tailMs) so the next screen never arrives mid-sentence. Only the step that starts a cue waits — consecutive steps sharing a line are one cue, spoken once.

That max is also what keeps a good plan sounding slow. A hold is written for a silent recording; once the line explains the change, the same second of stillness is dead air on top of a sentence that already made the point. "fit": "line" hands the step's length to its own copy, and the walkthrough is as long as it has something to say — on the sign-in example that is 70% speech instead of 55%, 4.8 seconds of padding gone.

Two engines, one pipeline

The default is macOS say, because it is part of the operating system: no install, no key, no network. --narration-engine elevenlabs speaks each line over HTTPS instead, which is what a Linux host or CI uses, and what gives you a choice of voice on a Mac too. Only the synthesis differs — pacing, the .vtt, the cache and the mux are shared, so a line is timed the same way whichever engine said it.

ElevenLabs needs ELEVENLABS_API_KEY, from the environment or from a gitignored .env beside the plan (copy .env.example). The file is the safer of the two: a key exported in a shell is a key in a shell history, and a key set in a CI log is a key in a CI log. A name is resolved against the voices the key can see, which needs the voices_read permission; an id is used as given, so a key scoped to text-to-speech alone works.

Lines are read as one telling rather than six recordings: each request carries the sentence before and after it, which is what keeps the cadence and the emphasis moving across step boundaries instead of every line starting cold on a full stop. The delivery is the plan's, spelled out in full:

KeyWhat it changes
stabilityhow firmly one reading is held. High is flat and consistent; low carries emphasis but drifts between takes. The first knob to try — 0.35–0.45 is where a walkthrough starts to sound told
stylehow much the model exaggerates; a little goes a long way here
similarityBoosthow closely the output hugs the reference voice
speakerBoostthe service's presence pass
modeleleven_multilingual_v2 carries the cadence across steps; eleven_v3 and eleven_v4 reject the neighbours and read every line alone, so the run says so and drops them

The delivery keys are inert for say, and a plan that sets them without "engine": "elevenlabs" is warned about instead of silently doing nothing. Editing a line re-speaks it and its two neighbours and nothing else: the delivery and the surrounding sentences are part of the cache key, because the same words at another stability are another reading.

Choose the voice by ear

A voice, a copy register and a stability are judgements of sound, and prose cannot make them. scripts/voice-audition.mjs speaks the same six steps eight ways — four registers of the copy, two models, two stabilities, two voices — and writes one page with a player per variant and the finished recording beside them: 

node scripts/voice-audition.mjs --out captures/audition

This page does not play a narrated recording, and that is deliberate: a narration needs an API key and a system ffmpeg with libopus, so it is not something the gallery can build from this repository alone. The audition renders the variants locally in one command, from the key in your .env.

Examples

Every recording below was made by this tool from a plan in this repository, against the bundled example app — no account, no network. Click a card to watch it in a window you can actually read; the review sheet is the run directory's own page, where a reviewer steps through the figures.

The same sidebar, three palettes

One plan, three themes. The chrome's colours are tokens, so a plan names a palette instead of a stylesheet: "video": { "theme": "memory" } is the product's own dark theme, and dracula and catppuccin-mocha ship beside it. A preset holds literal values, so it renders on a page that defines no CSS of its own.

The three panels below are not screenshots. Each one is the recorder's own panel stylesheet with that preset's tokens set — the chrome drawn in this page, at this page's size, so it stays sharp and cannot go stale independently of the chrome it shows. Two of the presets document nothing but colour; memory also names the product's radius and font, because it is the product's theme and the panel should look like part of it.

06

What a run writes

captures/signin-2026-01-01T10-00-00/
  review.html          ← open this: every figure, its size, the text it asserted,
                          and a slideshow that walks them in the run's order
  01-signin.png        ← the figure, at the capture ratio
  02-app.png
  .shots.json          ← capture ratio per figure (real px → CSS px)
  .timeline.json       ← where each step started and ended, and the video chapters
  failures/            ← only on failure: the page, its DOM, and its controls
  trace.zip, video/    ← only with --trace / --video
  video/01-main.webm   ← the recording; the voice is muxed into this file
  video/01-main.vtt    ← subtitles: the speech when narrated, else the captions

A run directory is reviewable before it touches a document. That is the point of the default: nothing overwrites a published figure until a human has looked at review.html.

Captures are run output, not source — keep them out of the repository and out of the review, or the diff becomes a folder of PNGs nobody reads.
